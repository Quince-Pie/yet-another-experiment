### A.1 Subject computation (`src/subject.ts`)
- Exactly one of `subject-path`, `subject-digest`, `subject-checksums` (`subject.ts:50-77`); if none, subjects are discovered from the runner file `$GITHUB_ARTIFACTS_LIST` (`subject.ts:53-71`, `src/artifacts.ts:5-12`, JSON `{version:1, subjects:[{name,digest:"sha256:hex",kind:"file"|"oci"}]}`), else error "One of subject-path, subject-digest, or subject-checksums must be provided" (`subject.ts:68-70`).
- `MAX_SUBJECT_COUNT = 1024` (`subject.ts:13`); enforced for globbed files (`subject.ts:127-131`) and discovered lists (`subject.ts:60-64`). Checksums file max size `512*1024` bytes (`subject.ts:14,224-228`).
- `subject-path`: parsed as CSV/newline list (`subject.ts:117,303-318`, csv-parse with `relaxQuotes`, trimmed), expanded with `@actions/glob` (`subject.ts:120`, `glob.create(...).glob()`), then **only regular files are kept** (`subject.ts:124-134`, `stat.isFile()`); directories themselves are dropped. `@actions/glob 0.7.0` defaults `implicitDescendants: true, matchDirectories: true, followSymbolicLinks: true` (toolkit `packages/glob/src/internal-glob-options-helper.ts:9-13`); with implicit descendants a pattern not ending in `**` gets a `pattern/**` sibling (`packages/glob/src/internal-globber.ts:70-81`) and directories are recursed via `readdir` (`internal-globber.ts:137-152`). Net effect: `subject-path: dist/` attests **every file under `dist/` recursively**.
- Subject name = `subject-name` if given, else **basename only** `path.parse(file).base` (`subject.ts:137`); digest = streamed `sha256` (`subject.ts:15,138,290-301`). Dedupe only when name AND digest equal (`subject.ts:141-147`); two different files with the same basename both appear under the same name. Empty match → error `Could not find subject at path …` (`subject.ts:150-152`).
- `subject-digest`: `algorithm:hex` where algorithm ∈ {sha224, sha256, sha384, sha512, sha512_224, sha512_256} with length check (`subject.ts:19-26,160-188`); requires `subject-name` (`subject.ts:79-81`).
- `subject-checksums`: path to a file (or an inline string if the path does not exist, `subject.ts:204-213`); shasum-style lines `hex[space][*| ]name`, split on `\r?\n` (`subject.ts:240-257`); algorithm inferred from hex length 64→sha256, 128→sha512 (`subject.ts:320-328`); names with newlines rejected (`subject.ts:263-265`); deduped (`subject.ts:276-281`).
- `push-to-registry` lowercases the name (`subject.ts:85`) and requires exactly one sha256 subject (`src/main.ts:277-293`).

### A.2 SLSA predicate (toolkit `packages/attest/src/provenance.ts`, main@193fa46c, version 3.2.0)
- Statement: `_type: https://in-toto.io/Statement/v1` (`intoto.ts:3,26-31`), `predicateType: https://slsa.dev/provenance/v1` (`provenance.ts:5,38`), `buildType: https://actions.github.io/buildtypes/workflow/v1` (`provenance.ts:6,41`).
- Inputs are claims from a **second** OIDC token requested with audience `nobody` (`oidc.ts:5,36`), verified locally against the issuer JWKS (`oidc.ts:50-53`, `oidc.ts:68-85`, issuer `https://token.actions.githubusercontent.com` derived from `GITHUB_SERVER_URL`, `oidc.ts:102-117`). Required claims `oidc.ts:12-25`: iss, ref, sha, repository, event_name, job_workflow_ref, workflow_ref, repository_id, repository_owner_id, runner_environment, run_id, run_attempt.
- Fields (`provenance.ts:37-75`):
  - `externalParameters.workflow.ref` = `claims.ref` (line 44), `.repository` = `${GITHUB_SERVER_URL}/${claims.repository}` (45), `.path` = `workflow_ref` with `repository/` prefix removed and `@ref` split off (33-35, 46).
  - `internalParameters.github` = `{event_name, repository_id, repository_owner_id, runner_environment}` (50-55).
  - `resolvedDependencies[0]` = `{uri: git+${server}/${repository}@${ref}, digest: {gitCommit: claims.sha}}` (57-64).
  - `runDetails.builder.id` = `${server}/${claims.job_workflow_ref}` (67-69); `runDetails.metadata.invocationId` = `${server}/${repository}/actions/runs/${run_id}/attempts/${run_attempt}` (70-72).
- Real example (cli/cli v2.101.0, produced by actions/attest v4.2.2, file `research/sample/user.sigstore.json`): `workflow.ref: refs/heads/trunk`, `repository: https://github.com/cli/cli`, `path: .github/workflows/deployment.yml`, `resolvedDependencies[0].uri: git+https://github.com/cli/cli@refs/heads/trunk`, `gitCommit: 0cf1092…`, `builder.id: https://github.com/cli/cli/.github/workflows/deployment.yml@refs/heads/trunk`, 21 subjects.
- **Pinning "workflow X at refs/tags/vY from commit Z"**: two layers.
  1. Certificate extensions (set by Fulcio from the signing OIDC token; not writable by the workflow): SAN = `{{ .url }}/{{ .job_workflow_ref }}` (fulcio `config/identity/config.yaml:209`; `pkg/identity/ciprovider/principal.go:145-160` sets `cert.URIs`), i.e. `https://github.com/OWNER/REPO/.github/workflows/release.yml@refs/tags/v1.2.3`. Also `build-signer-uri` (1.9, same value, `config.yaml:183`), `build-config-uri` (1.18, `{{ .url }}/{{ .workflow_ref }}`, `:199`), `source-repository-ref` (1.14, `ref`, `:191`), `source-repository-digest` (1.13, `sha`, `:190`), `source-repository-uri` (1.12, `:189`), `build-signer-digest` (1.10, `job_workflow_sha`, `:185`), `build-trigger` (1.20, `event_name`, `:202`), `runner-environment` (1.11, `:187`), `run-invocation-uri` (1.21, `:205`), `source-repository-visibility-at-signing` (1.22, `:207`); deprecated 1.2–1.6 (`github-workflow-{trigger,sha,name,repository,ref}`, `config.yaml:173-181`) are still populated.   2. Predicate fields above (signed, but produced inside the workflow job from the same claims). gh's own help (`pkg/cmd/attestation/verify/verify.go:113-127`): only `signature.certificate` and `verifiedTimestamps` "cannot be manipulated by the workflow that originated the attestation"; `statement.predicate` can be falsified by an attacker controlling the job.

### A.3 Signing flow (toolkit `packages/attest/src`)
- `attest()` (`attest.ts:49-88`): builds statement → `signPayload` with payload type `application/vnd.in-toto+json` (`attest.ts:11,70-75`) → `writeAttestation` unless `skipWrite` (`attest.ts:79-85`; the action never sets `skipWrite`).
- Signing OIDC token: `CIContextProvider(OIDC_AUDIENCE='sigstore')` (`sign.ts:12,73`); the provider reads `ACTIONS_ID_TOKEN_REQUEST_URL/TOKEN` and appends `audience=sigstore` (bundled `attest/dist/index.js:65995-66020`). Missing `id-token: write` → error at `actions/attest/src/main.ts:69-73`.
- Instance selection (`actions/attest/src/main.ts:62-66`): `'public-good'` iff `github.context.payload.repository?.visibility === 'public' && !privateSigning`, else `'github'`. Source of truth is the **event payload** (`GITHUB_EVENT_PATH`), not the OIDC `repository_visibility` claim. **UNVERIFIED**: which event payloads lack `repository.visibility` (they would silently fall back to the GitHub instance).
- Endpoints (`endpoints.ts`): public-good = Fulcio `https://fulcio.sigstore.dev` + Rekor `https://rekor.sigstore.dev`, **no TSA** (`endpoints.ts:6-7,17-20`); github = Fulcio `https://fulcio.githubapp.com` + TSA `https://timestamp.githubapp.com`, **no Rekor** (`endpoints.ts:44-55`; for GHE hosts `fulcio.<host>`/`timestamp.<host>`).
- Witnesses (`sign.ts:76-104`): `RekorWitness` only when `rekorURL` set (`fetchOnConflict: true`), `TSAWitness` only when `tsaServerURL` set; timeout 10 s, 3 retries (`sign.ts:13-14`). So public repos get a Rekor entry and no RFC 3161 timestamp; private repos get a TSA timestamp and no Rekor entry. Confirmed on the real public bundle: 1 tlog entry `kind dsse / 0.0.1`, `inclusionProof` (with checkpoint) and `inclusionPromise` present, `logIndex 2846538553`, `integratedTime 1789482143`, zero `rfc3161Timestamps`.
- Rekor entry type: `RekorWitness` passes no `entryType`, and `toProposedEntry` defaults to `'dsse'` (`attest/dist/index.js:66601-66610,66749-66760`) → Rekor kind `dsse` v0.0.1.
- Bundle: `DSSEBundleBuilder({signer, witnesses})` (`sign.ts:108`); `certificateChain` defaults to `false` (`dist/index.js:65520-65523`) → `toDSSEBundle` picks `BUNDLE_V03_MEDIA_TYPE` = `application/vnd.dev.sigstore.bundle.v0.3+json` (`dist/index.js:60406-60410,60482`); verification material carries a single `certificate` (`attest.ts:92-103` handles both `certificate` and legacy `x509CertificateChain`). Confirmed on the real bundle (`mediaType application/vnd.dev.sigstore.bundle.v0.3+json`, keys `certificate, timestampVerificationData, tlogEntries`).
- Serialized with `bundleToJSON` (`attest.ts:81,112`, protobuf-specs JSON). Certificate lifetime on the sample: 10 minutes (`notBefore Sep 15 14:22:23 2026`, `notAfter 14:32:23`), issuer `O=sigstore.dev, CN=sigstore-intermediate`.

### A.4 Storage and the bundle file
- Upload: `POST /repos/{owner}/{repo}/attestations` with body `{bundle}` via Octokit with `@octokit/plugin-retry`, 5 retries (`store.ts:6-7,20-49`), `User-Agent: @actions/attest-3.2.0[ actions_orchestration_id/…]` (`internal/utils.ts:3-15`). Returns the attestation `id`; the action outputs `attestation-id` and `attestation-url` = `${serverUrl}/${owner}/${repo}/attestations/${id}` (`main.ts:134-137,245-246`). Needs `attestations: write` (README `actions/attest/README.md:64-76`).
- Bundle file: yes. `bundle-path` = `${RUNNER_TEMP}/<mkdtemp>/attestation.json` (`main.ts:26,99-100,234-243`); contents `JSON.stringify(att.bundle) + EOL` (`main.ts:113-116`). Each path is also appended to `${RUNNER_TEMP}/created_attestation_paths.txt` (`main.ts:27,118-131`; README `actions/attest/README.md:21-25`). The write happens **after** `createAttestation` returns (`main.ts:102` vs `:113`), i.e. after the API upload.
- Retrieval endpoints observed in gh: `GET /repos/{owner}/{repo}/attestations/{digest}` and `GET /orgs/{owner}/attestations/{digest}` (`cli pkg/cmd/attestation/api/client.go:117,123`). Response entries `{repository_id, bundle_url, initiator, bundle}` (`api/attestation.go:13-17`); in practice `bundle` was `null` and `bundle_url` pointed to `https://tmaproduction.blob.core.windows.net/attestations/<repo_id>/<date>/<id>.json.sn?<SAS>`; content is raw snappy-compressed bundle JSON (gh decodes with `klauspost/compress/snappy` `client.go:255-263`; decodable with `snzip -d -t raw`).

### A.6 Inputs and failure behavior
- `show-summary` (default true): adds heading + attestation URL to the step summary (`main.ts:145-147,222-232`).
- `push-to-registry` (default false): after signing, pushes the bundle to the OCI registry via `@sigstore/oci attachArtifactToImage` (`src/attest.ts:45-65`), then, if `create-storage-record` (default true) and the owner is an org, calls `POST /orgs/{owner}/artifacts/metadata/storage-record` (toolkit `artifactMetadata.ts:6-7`); storage-record failures only `core.warning` (`src/attest.ts:73-110`). Irrelevant for file subjects.
- `github-token` (default `${{ github.token }}`): used for the attestations POST (`store.ts:26`) and, with push-to-registry, `GET /repos/{owner}/{repo}` (`src/attest.ts:119-126`).
- Failure after signing: `writeAttestation` wraps any error as `Failed to persist attestation: …` (`store.ts:50-53`) → `attest()` rejects → `run()` catches and `core.setFailed` (`main.ts:148-153`). Because the file write is after the upload, **no bundle file is written on upload failure**, although the `bundle-path` output was already set (`main.ts:100`). There is no input to skip the upload (`skipWrite` exists only in the library, `toolkit attest.ts:38-39`). A Rekor failure (public-good) also fails the action (witness inside `signPayload`).

## B. gh `attestation verify` / `download` (cli/cli v2.101.0 @ 0cf10924)

### B.1 verify
- Usage `verify [<file-path> | oci://<image-uri>] [--owner | --repo]`; exactly one positional (`verify/verify.go:26-27`); `--owner`/`--repo` mutually exclusive and one required (`verify.go:239-243`). GHES hosts rejected (`auth/host.go:9-16`, "gh attestation does not currently support GHES").
- **Authentication**: the root command's `PersistentPreRunE` blocks any command when no token is configured (`pkg/cmd/root/root.go:83-93`, uses `cmdutil.CheckAuth`: env token or any host in hosts.yml, `pkg/cmdutil/auth_check.go:29-39`). `verify` marks the `--bundle` flag with `DisableAuthCheckFlag` (`verify.go:236-237`; mechanism `auth_check.go:21-27,41-66`), so **with `--bundle` no token is needed**; the HTTP client is built regardless (`verify.go:171-179`) but adds `Authorization` only if a token exists (`api/http_client.go:172-187`). Without `--bundle`, the API path runs and the token must be valid: empirical `GH_TOKEN=bogus` → `HTTP 401: Bad credentials (https://api.github.com/repos/cli/cli/attestations/sha256:…?per_page=30&predicate_type=https%3A%2F%2Fslsa.dev%2Fprovenance%2Fv1)`; no token → `To get started with GitHub CLI, please run: gh auth login` (exit 4). `trusted-root` uses `DisableAuthCheck` (`trustedroot/trustedroot.go:110`) and works with no token (empirical).
- API fetch (`verify/attestation.go:13-39`): `FetchParams{Digest, Limit, Owner, PredicateType, Repo, Initiator: "user"}`; URL `repos/{owner}/{repo}/attestations/{digest}` or `orgs/{owner}/attestations/{digest}` with `per_page` (≤100) and `predicate_type` (`api/client.go:104-137`); pagination with retry on 5xx (`client.go:139-194`); entries filtered to `initiator == "user"` (`client.go:165-173`); then `bundle_url` is fetched with the **external** (unauthenticated) client, snappy-decoded and `protojson`-unmarshalled (`client.go:196-277`); falls back to inline `bundle` if `bundle_url` empty (`client.go:205-212`). Empirical unauthenticated `curl` to the repo endpoint for public repo cli/cli returned **HTTP 200** with the attestation list; the org endpoint returned **401**. GitHub REST docs for "List attestations" say "The authenticated user making the request must have read access to the repository … when using a fine-grained access token the attestations:read permission is required" — the documented rule and observed anonymous 200 differ; **UNVERIFIED** whether anonymous access is guaranteed.
- Observed `initiator` values on cli/cli v2.101.0 assets: `"user"` (the workflow's actions/attest attestation, SLSA provenance) and `"github"` (a second bundle signed by GitHub's own Fulcio: issuer `O=GitHub, Inc., CN=Fulcio Intermediate l1`, subject `CN=Attester`, SAN `https://dotcom.releases.github.com`, 1-year cert, TSA timestamp only, no Rekor; statement `predicateType https://in-toto.io/attestation/release/v0.2`, subject `pkg:github/cli/cli@v2.101.0` with sha1 commit digest, predicate keys databaseId/ownerId/packageId/purl/repository/repositoryId/tag). gh verify's `Initiator: "user"` filter drops these; `download` does not filter (`download/download.go:137-142` sets no Initiator). Docs only say "You can also generate release attestations … see Immutable releases". **UNVERIFIED** semantics of the GitHub-initiated release attestation.

## F. Example verification commands (blob `release.json`, bundle `release.json.sigstore.json`, workflow `.github/workflows/release.yml` in `OWNER/REPO` at `refs/tags/v1.2.3`, commit `COMMIT`)

Producer side (public repo): `actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2` with `subject-path: release.json` (or a checksums file); copy `${{ steps.attest.outputs.bundle-path }}` to `release.json.sigstore.json` and upload it as a release asset. Permissions `id-token: write`, `attestations: write`, `contents: write` (release upload).

gh (no token needed; needs `.json`/`.jsonl` extension):
```
gh attestation trusted-root > trusted_root.jsonl        # once, online
gh attestation verify release.json --repo OWNER/REPO \
  --bundle release.json.sigstore.json \
  --custom-trusted-root trusted_root.jsonl \
  --cert-identity 'https://github.com/OWNER/REPO/.github/workflows/release.yml@refs/tags/v1.2.3' \
  --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --predicate-type https://slsa.dev/provenance/v1 \
  --source-ref refs/tags/v1.2.3 --source-digest COMMIT \
  --deny-self-hosted-runners --format json
# looser: --signer-workflow OWNER/REPO/.github/workflows/release.yml   (prefix regex, any ref)
# online alternative (needs a valid GH_TOKEN of any account): gh attestation verify release.json --repo OWNER/REPO --signer-workflow OWNER/REPO/.github/workflows/release.yml
```

cosign v3.1.3:
```
head -1 trusted_root.jsonl > trusted_root_pgi.json     # public-good line (or omit --trusted-root to use TUF online)
cosign verify-blob-attestation release.json \
  --bundle release.json.sigstore.json \
  --trusted-root trusted_root_pgi.json \
  --certificate-identity 'https://github.com/OWNER/REPO/.github/workflows/release.yml@refs/tags/v1.2.3' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-repository OWNER/REPO \
  --certificate-github-workflow-ref refs/tags/v1.2.3 \
  --certificate-github-workflow-sha COMMIT \
  --type https://slsa.dev/provenance/v1
```

sigstore-python:
```
sigstore verify github release.json \
  --bundle release.json.sigstore.json \
  --cert-identity 'https://github.com/OWNER/REPO/.github/workflows/release.yml@refs/tags/v1.2.3' \
  --repository OWNER/REPO --ref refs/tags/v1.2.3 --sha COMMIT --trigger release \
  [--offline]
# prints the in-toto statement; check predicateType/predicate yourself (e.g. pipe to jq)
```

slsa-verifier v2.7.1 (online TUF; only if the signer ran at a vX.Y.Z tag):
```
slsa-verifier verify-github-attestation release.json \
  --attestation-path release.json.sigstore.json \
  --source-uri github.com/OWNER/REPO \
  --builder-id https://github.com/OWNER/REPO/.github/workflows/release.yml \

```

## G. Unresolved gaps
1. Anonymous access to `GET /repos/{owner}/{repo}/attestations/{digest}` worked for a public repo but docs state read access is required; treat anonymous API fetch as unguaranteed. The org endpoint requires auth.
2. Meaning and guarantees of GitHub-initiated (`initiator: "github"`) release attestations (`https://in-toto.io/attestation/release/v0.2`, signed by GitHub's Fulcio with a 1-year cert, SAN `https://dotcom.releases.github.com`) are undocumented in the pages fetched.
3. Which npm-published `@actions/attest@3.2.0` commit corresponds to toolkit main (candidates `7987771a`, `69f29a1b`); verifiable via npm provenance.
4. Cause of the incomplete `dist/licenses.txt` and the stale `dist/184.index.js` in actions/attest v4.2.2.
5. Event payloads lacking `repository.visibility` would silently switch a public repo to GitHub's private Sigstore instance (TSA-only, no Rekor); public-good-only verifiers (cosign/sigstore-python defaults) would then fail.
6. cosign/sigstore-python behavior on GitHub-instance (TSA-only) bundles not exercised.
7. slsa-verifier does not verify the Rekor inclusion proof itself (only SET + signature match were read; `rekor.go` not fully audited) — UNVERIFIED.
