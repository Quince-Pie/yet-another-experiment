### 2.1 How `github:` and `git+https` actually behave (Nix 2.34.8 source, NixOS/nix @ 8f7ed1c)

`src/libfetchers/github.cc`:
- ref → rev resolution hits the REST API: line 417 `"https://api.%s/repos/%s/%s/commits/%s"` (returns `sha` and `commit.tree.sha`, lines 430-431). This happens whenever the flakeref names a branch/tag (e.g. `github:OWNER/REPO/v1.2.3`) and the result is not already locked/cached.
- tarball URL: lines 440-444 — comment `// If we have no auth headers then we default to the public archive urls so we do not run into rate limits.`; without a token it uses `https://%s/%s/%s/archive/%s.tar.gz` (github.com, not api.github.com), with a token `https://api.%s/repos/%s/%s/tarball/%s`.
- lock semantics: lines 353-357 `/* Since we can't verify the integrity of the tarball from the Git revision alone, we also require a NAR hash for locking. FIXME: in the future, we may want to require a Git tree hash instead of a NAR hash. */` → `isLocked` = rev present && (trustTarballsFromGitForges || narHash present).
- the comparison of the unpacked tree's git tree hash against the API's `commit.tree.sha` exists but is compiled out (`#if 0`, lines 323-330).
- Manual (P, https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake.html): github inputs "are downloaded as tarball archives, rather than through Git. This is often much faster and uses less disk space since it doesn't require fetching the entire history."; `revCount` unavailable for github:; lock `narHash` "the expected contents of the tree in the Nix store".
- Rate limits (P, https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api): "The primary rate limit for unauthenticated requests is 60 requests per hour." (per IP); authenticated "5,000 requests per hour"; "The rate limit for `GITHUB_TOKEN` is 1,000 requests per hour per repository." Nix `access-tokens` setting (P, https://nix.dev/manual/nix/latest/command-ref/conf-file.html): "Access tokens are specified as a string made up of space-separated `host=token` values", e.g. `access-tokens = github.com=23ac...b289`. `install-nix-action` exposes `github_access_token` "to help work around rate limit issues" (P, README).
- Archive REST endpoint (P, https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-tar): `GET /repos/{owner}/{repo}/tarball/{ref}` "Gets a redirect URL to download a tar archive"; "For private repositories, these links are temporary and expire after five minutes."

`src/libfetchers/git.cc` (git+https etc.): attributes `shallow` ("Make a shallow clone when fetching the Git tree. When this is enabled, the options `ref` and `allRefs` have no effect anymore.", :272-273), `submodules`, `lfs`, `exportIgnore`, `allRefs`, and `verifyCommit`/`keytype`/`publicKey`/`publicKeys` which require the experimental feature `verified-fetches` (:388-389). `publicKey` defaults `keytype` to `ssh-ed25519` (:155-157).

**X — narHash equality across fetchers (numtide/treefmt-nix @ 27b3b12, no `.gitattributes`):**
```
github: fetcher            sha256-WSFCsDSE5ffgD2MqzkM2CYjeFiKhRF/dJUN8uedb6YE=

A flake that must hash identically under both fetchers must not use those attributes.

### 2.2 The January 2023 archive-checksum incident and GitHub's policy (P)

- https://github.blog/open-source/git/update-on-the-future-stability-of-source-code-archives-and-hashes/ (2023-02-21): on 2023-01-30 GitHub deployed Git 2.38, which "changed the default compression command used for `git archive` generation from external `gzip` to an internal copy of `gzip`"; "small changes to compression settings meant that the byte layout of the archive itself changed. This in turn meant that any hash or checksum (think SHA256, CRC64, etc.) of the archive also changed." Rolled back. Policy: "GitHub will hold the source downloads byte-for-byte stable for no less than a year from today (February 21, 2023). This covers both tarball (.tar.gz) and zipball (.zip) formats."; "if we intend to change either archive format, we'll provide six months' notice in documentation, and on the blog and changelog."; "We presently have no intent to change either format".
- Current docs https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives ("Stability of source code archives"): archives are generated on request and not kept; "An archive of a commit ID will always have the same file contents whenever it's requested, assuming the commit ID is still in the repository and the repository's name has not changed."; compression may change the outer bytes while contents stay; recommends "the archives REST API with a commit ID for `:ref`" for reproducibility and "releases instead of using source downloads" for security. URL forms: `/archive/refs/tags/<tag>.tar.gz`, `/archive/<sha>.tar.gz`.
- Git 2.38 release notes (P, `Documentation/RelNotes/2.38.0.adoc`): "Teach "git archive" to (optionally and then by default) avoid spawning an external "gzip" process when creating ".tar.gz" (and ".tgz") archives."

**Why narHash is unaffected (P + X):** `nix hash path` = "print cryptographic hash of the NAR serialisation of a path" (P, https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-hash-path.html); NAR contains only file type, executable bit, contents, symlink targets, sorted directory entries (§5). Experiment: same tar recompressed with `gzip -9n` → tarball sha256 changed (`d1122f7f…` → `dc8b75e5…`) but `nix flake prefetch tarball+file://…` narHash stayed `sha256-4+UgJM3Y…`. Real-world: GitHub's tarball (49742 B) vs local git 2.54 `git archive --format=tar.gz` (49220 B) differ as gzip streams but the **uncompressed tar streams are byte-identical (409600 B)** and narHash identical. So the only hashes that can break from a compression change are hashes of the `.tar.gz` bytes (nixpkgs `fetchurl`-style), never `narHash`/`fetchzip`/flake locks.

## 3. Supply-chain / security frameworks

### 3.1 SLSA (current spec = **v1.2, "Approved"**; v1.1 page shows "Retired") — P https://slsa.dev/spec/ , https://slsa.dev/spec/v1.2/build-requirements , https://slsa.dev/spec/v1.2/source-requirements
- Build L1 "Provenance Exists": "The build process MUST generate provenance that unambiguously identifies the output package by cryptographic digest and describes how that package was produced."
- Build L2 "Provenance is Authentic": consumers validate via digital signature; "The data in the provenance MUST be obtained from the build platform"; hosted, not workstations.
- Build L3 "Provenance is Unforgeable" + "Isolated": "Any secret material used for authenticating the provenance...MUST be stored in a secure management system...and accessible only to the build service account" and "MUST NOT be accessible to the environment running the user-defined build steps"; platform must "prevent runs from influencing one another, even within the same project", ephemeral environments, no cross-build cache poisoning.
- Producer: "MUST select a build platform that is capable of reaching their desired SLSA Build Level"; "MUST distribute provenance to artifact consumers".
- **Source track (new in v1.x):** L1 "Version controlled"; L2 "History & Provenance" (immutable branch history + SCS-generated Source Provenance Attestations per revision); L3 "Continuous technical controls" ("The SCS is configured to enforce the Organization's technical controls for specific Named References"); L4 "Two-party review" ("Changes in protected branches MUST be agreed to by two or more trusted persons prior to submission") — L4 is unreachable for a single maintainer by definition.
- **GitHub artifact attestations** (P, https://docs.github.com/en/actions/concepts/security/artifact-attestations): "Artifact attestations by itself provides SLSA v1.0 Build Level 2."; reusable workflows "can provide isolation between the build process and the calling workflow, to meet SLSA v1.0 Build Level 3." Public repos use "the Sigstore Public Good Instance" with a public transparency log; private repos use "GitHub's Sigstore instance" (no transparency log). How-to (P, github/docs source): `uses: actions/attest@v4` with `permissions: id-token: write, contents: read, attestations: write`; verify `gh attestation verify PATH -R OWNER/REPO` (flags `--signer-workflow`, `--signer-repo`, `--source-ref`, `--deny-self-hosted-runners`, `--bundle` for offline, `--custom-trusted-root`; predicate default `https://slsa.dev/provenance/v1`). `actions/attest-build-provenance` latest v4.2.2.

- Consequence for this project: there is no build artifact; the "artifact" a CI attestation could cover is the NAR/tree digest of the tag's source. That attests "GitHub Actions observed tree T at commit C" (Build-track provenance for a source snapshot), and does not attest maintainer authorization — the Source track is the relevant frame, and its L2 "source provenance" is what GitHub's immutable-release attestation (tag+SHA) most closely supplies.

## 4. Signing the maintainer's authorization anchor

### 4.1 SSH signatures (git ≥ 2.34) — P git docs (`Documentation/config/gpg.adoc`, `user.adoc`, `git-tag.adoc` @ v2.54.0), gpg-interface.c @ v2.54.0, ssh-keygen(1) OpenBSD, GitHub docs
- `gpg.format`: "Specifies which key format to use when signing with `--gpg-sign`. Default is "openpgp". Other possible values are "x509", "ssh"."
- `user.signingKey`: "If gpg.format is set to `ssh` this can contain the path to either your private ssh key or the public key when ssh-agent is used. Alternatively it can contain a public key prefixed with `key::` directly (e.g.: "key::ssh-rsa XXXXXX identifier"). The private key needs to be available via ssh-agent."
- `gpg.ssh.allowedSignersFile`: "A file containing ssh public keys which you are willing to trust. The file consists of one or more lines of principals followed by an ssh public key. e.g.: `user1@example.com,user2@example.com ssh-rsa AAAAX1...` See ssh-keygen(1) "ALLOWED SIGNERS" for details."; `gpg.ssh.revocationFile`: "Either a SSH KRL or a list of revoked public keys ... If a public key is found in this file then it will always be treated as having trust level "never"".
- `git tag -s/--sign`: "Make a cryptographically signed tag, using the default signing key. The signing backend used depends on the `gpg.format` configuration variable."; `-v/--verify`: "Verify the cryptographic signature of the given tags."
- Git signs with `ssh-keygen -Y sign -n git -f <key> [-U]` (gpg-interface.c:1108-1114) and verifies with `ssh-keygen -Y find-principals -f <allowed_signers> -s <sig> [-Overify-time=…]` then `ssh-keygen -Y verify -n git -f <allowed_signers> -I <principal> -s <sig> [-Overify-time=…] [-r <revocation>]` (:504-509, :571-576). `verify-time` is the tag's timestamp formatted `%Y%m%d%H%M%S` in local time (:476-481), which is what makes `valid-after`/`valid-before` in allowed_signers apply at signing time; ssh-keygen(1): "verify-time=timestamp Specifies a time to use when validating signatures instead of the current time."
- ssh-keygen(1) ALLOWED SIGNERS: fields principals, options (`cert-authority`, `namespaces=namespace-list`, `valid-after=timestamp`, `valid-before=timestamp`), keytype, key; `-Y sign` "must be provided via the `-n` flag" a namespace "to prevent signature confusion across different domains of use"; `-Y verify` "Successful verification ... zero exit status"; `-Y check-novalidate` checks structure only; `-Y find-principals` finds the principal for a signature.
- GitHub (P, https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification and telling-git-about-your-signing-key): "SSH signature verification is available in Git 2.34 or later."; `git config --global gpg.format ssh` + `git config --global user.signingkey /PATH/TO/.SSH/KEY.PUB`; the "Verified" badge requires the key to be added to the account as a **signing** key ("Add a SSH signing key to your GitHub account"); signed tags are supported ("Sign tags" step). Rulesets "Require signed commits" ("contributors and bots can only push commits that have been signed and verified") can be applied to tag patterns.

**Exact commands (X — all run with git 2.54.0 / OpenSSH 10.5p1; outputs shown):**

(a) sign an annotated tag with an SSH key, no global config:
```
git -c gpg.format=ssh -c user.signingkey=/path/to/id_release.pub tag -s v1.0.0 -m 'Release v1.0.0'
# (or -c user.signingkey='key::ssh-ed25519 AAAA…' with the private key in ssh-agent)
```
(b) verify with git against an allowed_signers file:
```
printf 'maintainer@example.invalid namespaces="git" ssh-ed25519 AAAAC3Nza…\n' > allowed_signers
git -c gpg.format=ssh -c gpg.ssh.allowedSignersFile=$PWD/allowed_signers verify-tag v1.0.0
# → Good "git" signature for maintainer@example.invalid with ED25519 key SHA256:MFarx1vk…
```
(c) verify from the raw tag object with ssh-keygen only (no git config; needs only `git cat-file`, `sed`, `ssh-keygen`):
```
git cat-file tag v1.0.0 > tag.raw
sed -n '/^-----BEGIN SSH SIGNATURE-----$/,/^-----END SSH SIGNATURE-----$/p' tag.raw > tag.sig
sed '/^-----BEGIN SSH SIGNATURE-----$/,$d' tag.raw > tag.payload      # everything before the signature block
ssh-keygen -Y verify -f allowed_signers -I maintainer@example.invalid -n git -s tag.sig < tag.payload
# → Good "git" signature for maintainer@example.invalid with ED25519 key SHA256:MFarx1vk…   (exit 0)
ssh-keygen -Y find-principals -s tag.sig -f allowed_signers                                   # → maintainer@example.invalid
# tamper test: editing one byte of tag.payload → "Signature verification failed: incorrect signature" (exit 255)
# optional, to match git's validity-window semantics: -Overify-time=$(date -d @<tagger-epoch> +%Y%m%d%H%M%S)
```
The tag object layout confirmed by `git cat-file tag`: `object <sha>\ntype commit\ntag v1.0.0\ntagger …\n\n<message>\n-----BEGIN SSH SIGNATURE-----…-----END SSH SIGNATURE-----` (signature appended after the message; payload = everything before the `-----BEGIN` line).

### 4.2 OpenPGP
Used by NixOS/nix (§1.3: `git tag --force --sign`, public keys vendored under `maintainers/keys/*.asc`). GitHub "Verified" needs the GPG key on the account. Recipient verification needs gpg + key import + trust handling; no equivalent of the one-line allowed_signers file, no built-in Nix fetcher verification (Nix `verifyCommit` is SSH-only).

### 4.3 gitsign (Sigstore keyless for commits/tags) — P README https://github.com/sigstore/gitsign ; GitHub API
- Latest **v0.17.1** (2026-08-05); repo not archived, `pushed_at` 2026-09-14 → maintained. nixpkgs `gitsign` 0.16.1.
- Mechanism: signs with an ephemeral key + Fulcio certificate bound to an OIDC identity; signature stored as CMS/PKCS7 in the commit/tag; Rekor entry (commit SHA online, or hashed content offline).
- Verification: "gitsign verify is preferred over git verify-commit and git verify-tag" (git alone cannot check "who put the data there"); needs the Sigstore trust root and Rekor (or offline bundle).
- Limitations quoted: "GitHub doesn't recognize Gitsign signatures as verified at the moment"; "Setting this will make git commit/tag reliant on internet"; browser OIDC flow per signing session unless credential cache is enabled.
- For this project: consumers would need gitsign + Sigstore trust root; Nix `verifyCommit` cannot consume it; no GitHub badge.

### 4.4 Sigstore keyless from CI — what it proves (P https://docs.sigstore.dev/cosign/signing/overview/ , Fulcio https://github.com/sigstore/fulcio/blob/main/docs/oid-info.md , GitHub OIDC doc)
- "An in-memory public/private keypair is created"; Fulcio "issues a certificate attesting to their identity. The identity is bound to the public key."; Rekor "witnesses" with a timestamped entry; "the private key is destroyed shortly after".
- For GitHub Actions the certificate carries (Fulcio OIDs 1.3.6.1.4.1.57264.1.x): Issuer (`https://token.actions.githubusercontent.com`), Build Signer URI/Digest (workflow ref + commit), Runner Environment, Source Repository URI/Digest/Ref/Identifier/Owner URI, Build Config URI/Digest, Build Trigger (e.g. `push`), Run Invocation URI, Source Repository Visibility. Verification requires `--certificate-identity` and `--certificate-oidc-issuer`.
- Therefore a CI keyless signature proves: *this exact workflow file at this commit, in this repo, ran on GitHub-hosted infra on trigger T and signed digest D*. It does **not** prove the maintainer authorized the tag: anyone able to push a matching tag (or anything with `contents: write` on the repo) obtains an identical identity. It is provenance of observation, not authorization. The maintainer-held SSH key (offline, never in CI) is the only anchor here that a `GITHUB_TOKEN`/Actions compromise cannot mint.

## 5. Reproducible / canonical source archives

- **NAR** (P, Nix manual "Nix Archive (NAR) format", Nix 2.35.2 manual): includes regular files (with optional executable bit and contents), symlinks (target), directories with entries that "must be ordered by their names"; excludes timestamps, permissions other than executable, ownership; strings length-prefixed (64-bit LE) and 8-byte padded; grammar `nar = str("nix-archive-1"), nar-obj;`. Tools: `nix nar pack DIR | sha256sum` == `nix hash path --type sha256 --base16 DIR` (X: `e3e52024cdd8…` both) == `nix flake prefetch` hash (SRI).
- **`git archive` determinism** (P, `archive-tar.c` @ v2.54.0 + git-archive(1)): ustar headers with `mtime = args->time` (commit time: "Without this option the committer time is used if <tree-ish> is a commit or tag, and the current time if it is a tree."; `--mtime=<time>` overrides), `uid`/`gid` = 0, `uname`/`gname` = "root", devmajor/minor 0, magic "ustar"/"00" (:218-238); a `pax_global_header` entry carrying `comment=<commit id>` (:330-360; retrievable with `git get-tar-commit-id`); since 2.38 the default `tar.gz` filter is the internal `git archive gzip` (:469, :534-536) using zlib with header `{ .os = 3 } /* Unix, for reproducibility */` (:474) and mtime 0 → gzip header bytes observed `1f 8b 08 00 00000000 00 03` for both GitHub's and local output. **No stability guarantee is stated in git-archive(1)** (grep for stable/reproducible/byte/identical/deterministic: none). Contents also depend on `.gitattributes` `export-ignore`/`export-subst` (and `--worktree-attributes`).
- **GitHub tarball hash stability**: policy in §2.2 (one-year byte stability from 2023-02-21, then six months' notice; contents-of-commit-ID always identical). X: GitHub's tarball for treefmt-nix@27b3b12 vs local git 2.54 `git archive`: uncompressed tar **identical** (409600 B; first 1024 B identical incl. pax header), gzip stream **different** (49742 vs 49220 B). ⇒ do not publish or promise `.tar.gz` byte hashes; the uncompressed tar or the NAR are the byte-stable forms.
- **Canonical archive form matching Nix consumers**: the **NAR of the tag's tree** (= `narHash` in every consumer's flake.lock, identical across `github:`, `git+https`, `tarball+…`, and `git archive | tar x`, X §2.1). A release can publish `nix hash path` (SRI) for the tag and, if an artifact is wanted, `nix nar pack` output (`.nar`, optionally compressed — but hash the `.nar`, not the compressed bytes). A `git archive --format=tar` (uncompressed) is a second byte-stable form; its digest is *not* what Nix checks.
